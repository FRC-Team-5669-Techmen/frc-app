2026-08-30 (Survey MANAGEMENT surface at /surveys -- list with eager response counts, delete, duplicate, title/window edit and CSV export -- plus the repo's first GitHub Actions workflow, .github/workflows/integrate.yml. See the two updated bullets in Built so far. THE QUESTION THAT HAD TO BE SETTLED BEFORE ANY OF IT COULD BE BUILT: does the migration's `revoke update, delete, truncate ... from authenticated` block the ON DELETE CASCADE that a survey delete depends on? ANSWERED BY RUNNING IT, not by reading the docs -- a local PostgreSQL 16 cluster with a modelled Supabase (anon/authenticated roles, auth.uid(), profiles, member_roles, is_staff(), and crucially the bootstrap ALTER DEFAULT PRIVILEGES, without which the revokes prove nothing because nothing was ever granted). IT DOES NOT BLOCK IT: as a staff caller under the `authenticated` role, `delete from public.surveys` took surveys 1->0, questions 5->0, responses 2->0 and answers 3->0, while the SAME role's direct `delete from survey_answers` and `delete from survey_responses` both raised 42501 permission denied. Those two direct deletes are the control, and they are the reason the cascade line means something rather than just 'authenticated could delete these anyway'. The mechanism is that a cascade is an internal referential-integrity trigger that runs as the OWNER of the referencing table with row security not forced, so the caller's table grants and RLS are simply not consulted for the rows it removes; only the initiating delete on surveys is checked, and a NON-staff caller's version of it removed nothing. So NO migration fix was needed for the cascade, and the file now carries the measurement plus an explicit 'do not fix this by granting delete on the child tables' -- that grant is unnecessary and would hand every member a direct delete on other people's submitted answers. THE OTHER PROVEN CLAIM: duplicating while another survey is open does not trip surveys_one_open_idx, because the copy is written is_open false and the index is partial `where is_open`. Measured on the real index -- the closed copy inserted fine and left `count(*) where is_open` at 1, and CONTROL D inserting the same copy with is_open true raised 'duplicate key value violates unique constraint surveys_one_open_idx', so the pass is not vacuous. The migration was amended IN PLACE with both records and re-applied twice to confirm it is still re-runnable. VERIFIED IN A BROWSER, 78/78: the real SurveysAdmin driven headless against a stubbed ./supabase (vite alias, no creds, no network, harness deleted after) whose in-memory store enforces surveys_one_open_idx, the ON DELETE CASCADE and survey_answers_nonempty_chk ITSELF, so a UI that got any of those wrong would fail rather than pass on a permissive fake. Covered: the list's response counts off a known fixture (3/1/0) with no row clicked and no leakage from the selected survey; the delete confirm naming 3 responses and 7 answers, 1 and 2 for a different survey, and 0 and 0 for an empty draft; the FIRST CLICK deleting nothing, asserted at the store; a real delete removing the survey, its questions, its responses and its answers while every other survey kept all of its rows; duplicate producing a CLOSED copy with identical prompts, kinds, options and required flags, positions renumbered, zero responses, no reused row ids, and exactly one survey still open throughout, with the original row proved byte-identical afterwards; a second duplicate counting the suffix up; title and window edits persisting to the store AND to the rendered row; and the pill flipping OPEN->EXPIRED when the close date is moved into the past with is_open left true, then back. CSV compared CELL FOR CELL against a hand-written fixture in both attribution states, including a comma in a prompt, a comma and double quotes in an answer, a joined multi-select, and two skipped questions that must be EMPTY cells rather than "" or []. A POSITIVE CONTROL runs the same diff function against a row wrong by one cell and asserts it reports 'row 2 col 2: got "Electrical" want "Programming"', plus a second control on a missing row -- so a green CSV check means something.

Until today every SQL file reached the live database by hand in the Supabase SQL editor, and nothing recorded which had run. idea-app solved the same problem with a seeded `supabase_migrations.schema_migrations` table and a Migrate workflow; this ports that design, cut down to what this repo needs.

**What landed.** `.github/workflows/migrate.yml` runs on a push to `main` touching `supabase/migrations/**`, and on demand with an optional dry run. Without the repository secret `SUPABASE_MIGRATE_DB_URL` it posts a notice and is green; with it, it runs `tools/apply-migration.mjs`. The tool creates the record table if missing (idea-app's name and shape: `version text primary key, statements text[], name text`), writes the baseline 0001 to 0026 with `on conflict do nothing` on every run, then applies every unrecorded `NNNN_name.sql` in number order, each in one transaction with its record row inside, stopping at the first failure. `_rls_test.sql` files and the frozen files are never selected, and a duplicated number refuses before connecting. A file with its own top-level `begin;` (0002 is the only one) goes unwrapped and is recorded after its own commit. `lock_timeout` is 15 s so a migration blocked by live check-ins rolls back rather than queueing every later query, and a session advisory lock prevents two appliers. The connection string and its password are redacted from every printed line.

**Why the bootstrap is not a numbered migration.** idea-app used a one-time paste (`supabase/data/0209-seed-migration-history.sql`) because its applier refused to run without a seeded table. Here the requirement was that the only manual step be the secret, so the bootstrap and the baseline live in the tool and run every time; there is nothing to paste and migration number 0031 was not taken. Writing the baseline on every run also means the tool cannot replay a hand-applied file even against an emptied table. The owner's statement of 2026-10-23 sets the baseline: everything through 0026 is applied (0022 to 0026 confirmed that day), 0027 and 0028 are not, so they are the first the workflow will apply.

**Deliberately not ported from idea-app:** the destructive-DDL scanner, the ledger `Migration permitted:` gate, per-object verification after apply, the catalog probe, and committing a record file back to `main` (a push to `main` redeploys the PWA here, so the workflow holds `contents: read` and writes nothing to git). No HTTPS proxy tunnel either: a GitHub runner needs none.

**Measured, 2026-10-23, in this container.** `npm run build` green; `npm test` 83 files, 1172 tests; `npm run ds:audit` ok (79 components, 315 files); `npm run discord:calendar:test` 19/19; `npm run history:verify` ok. `tests/apply-migration.test.js` is 19 tests (ordering, test-file exclusion, frozen-file exclusion, the baseline against the real file names, 0002 detected as self-managed, redaction, TLS settings), each exclusion paired with its inclusion; five in-memory mutants of the selector (test-file filter removed, directory filter removed, sort removed, recorded set ignored, 0026 dropped from the baseline) each turned it red (4, 2, 2, 3 and 2 failures), restored from a copy. `tests/workflows.test.js` gained three Migrate invariants. `node tools/sql-harness/run.mjs --migrations 0001-0026 --tests none --node tools/sql-harness/migrate-e2e.mjs` (the harness gained a range form of `--migrations`) passed 31/31: dry run wrote nothing and named 0027 then 0028; the real run created the table, recorded 26 baseline rows and applied 0027 and 0028 (their functions and tables then present in the catalog); a second run applied nothing and left 28 rows; a raising file rolled back, was not recorded and stopped the run before the next file, with the positive control that the fixed directory and a self-managed file both apply; the record schema has no USAGE for `anon` or `authenticated` (and does for `postgres`); the password appeared in none of seven outputs.

**Not verified.** Nothing touched the live project: this container cannot reach it, and no secret exists yet. Whether the live database already has a `supabase_migrations` schema (it would if the Supabase CLI ever pushed to it) is unknown; the bootstrap tolerates either. The workflow has never run on GitHub; its YAML is checked by `tests/workflows.test.js`, which is not GitHub's validator. Real Supabase TLS through the Session pooler is unexercised here (the harness is a local socket without TLS). A migration that reaches `main` through `deploy.yml` (a `GITHUB_TOKEN` push) does not start Migrate; it waits for the next qualifying push or a manual run. `CLAUDE.md` was already over its 4,000-word cap (4,180 by `wc -w`); this edit brought it to 4,173 and did not fix that.

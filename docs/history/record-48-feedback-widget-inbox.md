 Earlier the same day — In-app feedback widget + admin inbox at /feedback, plus the new public.is_admin() SQL helper. See the new bullet in Built so far. THE ONE DESIGN DECISION THAT DROVE THE REST: the storage bucket is PRIVATE, unlike the jobs bucket it is otherwise modelled on, because a feedback screenshot is a picture of the app mid-use and routinely has other members' names and hours in frame - which then forces signed URLs on the admin page, forces the Copy-for-Claude block to carry an image COUNT rather than a link, and is why the read policy is is_admin() rather than is_staff(). VERIFIED AGAINST A REAL POSTGRES, not by reading the SQL: a local PG16 cluster with a modelled Supabase (anon/authenticated roles, auth.uid(), a storage schema, and crucially the bootstrap ALTER DEFAULT PRIVILEGES grants, without which the anon case passes because nothing was ever granted). feedback.sql applies clean and is re-runnable; the new feedback_rls_test.sql returns 6 PASS. SEVEN NEGATIVE CONTROLS were run and the tree restored - widen select to using(true), insert with check(true), a permissive update policy, grant anon select back, select broken SHUT, add a delete policy+grant, and drop the update policy - and the FIRST RUN CAUGHT ONLY SIX. The miss is worth keeping: case 5 (a non-admin cannot update) passed even with a wide-open UPDATE policy, because an UPDATE has to FIND its rows and row lookup goes through the admin-only SELECT policy - so case 5 was really case 1 again and could never isolate what it claimed to. NEW case 5b reads pg_policies and requires every UPDATE policy to name is_admin() in both USING and WITH CHECK; it catches both the permissive-policy and the no-policy-at-all controls. TWO REAL FIXES CAME OUT OF RUNNING IT: the delete block was SILENT (0 rows, no error) until an explicit revoke delete, truncate from authenticated was added, and the storage delete policy's uploader half was found to be DEAD for non-admins for the same row-lookup reason - the comment claiming a member can undo their own upload was false and is corrected in the file rather than left standing. PASTE AND DRAG-AND-DROP WERE DRIVEN FOR REAL, not deferred: the actual FeedbackWidget in headless Chromium against a stubbed ./supabase, with genuine ClipboardEvent and DragEvent objects carrying a real DataTransfer holding a real decodable PNG - 33/34 (the one FAIL traced to the harness's own missing favicon.ico, confirmed by logging the console error's location). Paste works both with the caret in the textarea and dispatched on the panel with focus elsewhere; drop lights and clears the highlight; the picker is the third path; all three previews decode; a removal leaves the survivors rendering; the submitted row carries exactly seven keys with member_id from the session, route /jobs, viewport 420x860 matching the real window, and image_paths equal to the two uploaded uuid paths in the private bucket. A BUG WAS FIXED BEFORE IT SHIPPED, found while writing the cleanup rather than by the harness: the object-URL revoke was keyed on [images], which revokes the whole previous queue every time a file is added and breaks every preview already on screen - it is now unmount-only via a ref, with explicit revokes on remove and reset, and the harness's decode check is what pins it. The admin page was driven the same way: 36/36 including the clipboard read-back of both the single and bulk blocks, proving no signed URL and no token string survives into either. TWO HARNESS BUGS WERE FOUND BY RUNNING IT and neither was in the app: positional nth-child selectors silently addressed the wrong row (now addressed by content), and the stub ignored .order() so the newest-first check was testing the stub's array order.

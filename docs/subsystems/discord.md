# Discord

Moved verbatim from `CLAUDE.md` (The subsystems) on 2026-10-19, so `CLAUDE.md` stays short. `CLAUDE.md` links here; keep this file current in the same commit as any change to what it describes.

- **Discord server provisioning** (`scripts/discord/SERVER_SPEC.md` + `scripts/discord/provision.js` + `scripts/discord/README.md`). Ops tooling, NOT app code — it never imports from `src/` and ships nothing to the browser (`@discordjs/rest` + `discord-api-types` are devDependencies). Takes the team Discord guild from empty to fully configured in one run: guild settings → the two Community prerequisite channels → Community enablement (`PATCH /guilds/{id}` adding `COMMUNITY` to `features` with `rules_channel_id`/`public_updates_channel_id`) → roles → `@everyone` deny → categories → channels → AutoMod → onboarding. **`SERVER_SPEC.md` is the source of truth and is PARSED at runtime** — the role table, every channel permission matrix, the safety bullets and the onboarding questions — so a spec edit changes the plan with no second copy to sync. Only three vocabularies are hardcoded (colour word→hex, permission phrase→bitfield, `V`/`S`/`-`→overwrite) and each throws on an unknown token rather than dropping it. Dry run is the default and is read-only; `--apply` is required to write; `--offline` plans against a simulated empty guild with no token (and `--dump-state`/`--state` replay a plan over its own result to prove idempotency). **Idempotent, matched by name; never deletes** — anything in the guild but not in the spec is reported as UNMANAGED. Rate limits are honoured off the returned `retry_after`, never a fixed delay. Env: `DISCORD_BOT_TOKEN` + `DISCORD_GUILD_ID` from `process.env` or `.env.local` via `node --env-file`; npm scripts `discord:plan`/`discord:apply`/`discord:offline`. Unresolved spec ambiguities (what a roleless member sees, Student Lead's matrix row, `V`-and-reactions, hoist/mentionable, AutoMod exemptions) are listed in the README rather than silently decided.

- **Discord calendar posting** (`supabase/functions/discord-calendar/` — `index.ts` + `lib/{discord,render,calendarSync}.js` + `README.md`; `supabase/discord_calendar.sql`; `scripts/discord/calendar-sync.test.mjs`). Hourly pg_cron → pg_net → Edge Function posting `public.events` into the team Discord: one embed per upcoming event in **#calendar** (title, start/end in America/Los_Angeles, location, notes), plus a reminder in **#announcements** at 2h. **`reminder_24h` was RETIRED 2026-08-26** and is the one entry commented out of `REMINDERS` in `lib/calendarSync.js`; nothing else was removed. The Sunday week-ahead digest already says what is happening tomorrow, so the 24h reminder was the one duplicated post that also pinged a role, while the 2h reminder is same-day and nothing else covers it. Restoring that single array entry brings it back: the `reminder_24h` rendering path, its existing `discord_calendar_posts` dedupe rows and its `discord_calendar_log` rows are all deliberately intact, so already-posted 24h messages are still edited on a change and still struck through on a cancellation (the cancellation sweep walks the tracking table, never the `REMINDERS` array). `SHORTEST_LEAD_MS` is derived from `REMINDERS` rather than indexed into it, so adding or removing a lead cannot leave the supersede guard reading the wrong element. **Invocation auth matches send-push / cron-notify** — a shared secret in a custom header (`x-cron-secret` vs the `DISCORD_CRON_SECRET` function secret), **deploy `--no-verify-jwt`**, with `edge_base_url` + `hook_secret` in a private config table read only by a SECURITY DEFINER invoke function. That config is **`private.discord_calendar_config`, deliberately NOT `private.push_config`**: filling in push_config activates the push triggers/crons, and that deploy is still on hold, so sharing it would chain one release to the other. Null `edge_base_url` = the cron no-ops, which is the pause switch. **This is the one function in `supabase/functions/` that is NOT single-file** and so cannot be deployed from the Dashboard editor (`npx supabase functions deploy discord-calendar --no-verify-jwt`): `lib/` is the same code `scripts/discord/calendar-sync.test.mjs` imports under Node, and inlining it would mean two copies of the no-double-post logic. The engine is written to the **Deno∩Node intersection** — plain ESM, explicit file extensions on relative imports, nothing imported beyond `node:crypto` — so one copy runs in both; keep it that way. **FAILURE ISOLATION (2026-08-29): the cancellation sweep is NON-FATAL and read-only queries carry a bounded auth retry.** Production logged 9 fatal aborts in 168 hourly runs, all `loading cancellation candidates: JWT issued at future`, run_start 168 vs run_end 159. The sweep holds the run's FIRST PostgREST call, so a transient service-role JWT rejection (Edge-runtime clock ahead of the database, so `iat` looks future-dated) aborted the whole run before a single post was considered. The sweep only EDITS already-posted messages, so its failure is now caught at the call site, logged as `error` with `fatal: false` and `phase: 'cancellation_sweep'` (same detail shape, plus `summary.sweep_error`), and the run continues to posting and still writes `run_end`; the Edge Function still returns 200 because `ok` keys off `summary.fatal`. `readWithRetry` retries at most twice (250ms, 750ms, `config.sleep` injectable) and ONLY on an auth-shaped Supabase error (PGRST301/PGRST302, or `jwt`/`issued at`/`invalid claim` in message+hint+details), never on a `DiscordError` and never on a permission error like 42501 which is not transient. **It wraps SELECTs and nothing else** — that is the whole duplicate-post argument: a read cannot reserve a tracking row and cannot call Discord, so no number of attempts touches `unique (event_id, post_kind)`; the reserve-then-send path in `upsertPost` is deliberately NOT wrapped and must never be. **Widening the retry to all four reads was necessary, not incidental**: making only the sweep non-fatal would have moved the same fatal abort onto `loading events`, the next PostgREST call. **Still fatal, deliberately**: `resolveGuild` and a missing #calendar/#announcements channel (the channel id is written into the reserved tracking row, so continuing would burn a dedupe key against the wrong channel and permanently block the real post), `loading events` (the run's whole input), and `loading tracking rows` — that map IS the answer to what has already been posted, so proceeding without it sends every posted event down the CREATE branch; the unique constraint still blocks a duplicate message, but the run would stop editing changed messages and fill the log with false already_reserved skips, which is the duplicate-shaped failure the rule is about. **NEW log action `reminder_missed`** closes the silent-loss gap: when an event has started and no reminder row exists, the slot was closed with a `superseded` row indistinguishable from the routine planned close, so nobody-was-told looked identical to we-chose-not-to. `reminder_missed` is now logged first, carrying event_id, post_kind, lead, event_starts_at and minutes_late, exactly once per (event, kind) because the supersede row makes every later run take the `existing` branch. **No late reminder is posted and no Discord call is made** — it is a log row only. `auth_retry` is the other new action. Both, plus the `fatal` true/false split on `error`, are documented in `supabase/discord_calendar.sql`; `discord_calendar_log.action` is open text with no CHECK, so **neither needed a migration**. Test suite is 19 (was 13). **Report-only is the default** — only the literal `DISCORD_CALENDAR_MODE=live` enables writes, and report mode logs the intended posts WITHOUT reserving tracking rows, so dry runs never burn a dedupe key. **The no-double-post guarantee is a DB constraint, not app logic**: `discord_calendar_posts` is `unique (event_id, post_kind)` and every post is **reserve-then-send** (insert `status='pending'` → POST → update to `posted` + `message_id`), so overlapping runs race on the constraint and the loser posts nothing. A definitive 4xx releases the reservation (no message exists); an **ambiguous** failure (network drop, exhausted 429/5xx) deliberately KEEPS it as `pending` and never auto-retries — a visible stale row beats a duplicate ping to sixty people. **Changed event → the rendered payload hashes differently → the stored `message_id` is EDITED, never reposted.** **`discord_calendar_posts` deliberately has NO foreign key to `events`**: `public.events` has no `cancelled` column (staff cancel by DELETING the row via SchedulePage), so a cascade would destroy the evidence at the exact moment it is needed; the row plus its `event_snapshot` jsonb outlive the delete, and the sweep (`status='posted'` + `event_ends_at >= now()` + event id no longer present) edits the message to struck-through **CANCELLED** and keeps it. Deleted-after-it-ended is housekeeping, not a cancellation, and is left alone. `10008 Unknown Message` → row marked `archived`, never resurrected. **`events` has no subteam column either**, so "the event names a subteam" is taken literally. **`render.js` does NOT read `src/subteams.js`** (an earlier revision of this file said it did, which is wrong, and is what kept sending sessions in circles): it word-matches its OWN curated `SUBTEAM_ROLE_ALIASES` map over title+notes and emits SERVER_SPEC §3 Discord role names. That map is **11 alias entries resolving to 7 distinct roles** (Mechanical, Electrical, Programming, CAD, Business/Media, Scouting, Drive Team); several aliases fold onto one role (`business/outreach`, `business/media`, `business & media` and `media` all resolve to Business/Media) and two role names deliberately differ from the app's (`Business/Outreach` the subteam vs `Business/Media` the role, `Strategy and Scouting` the subteam vs `Scouting` the role). Fabrication/Robot Construction/Field & Pit have no Discord counterpart and intentionally ping nobody. `allowed_mentions` is pinned to the resolved role IDs with `parse: []`, so `@everyone` can never fire. **No snowflake is stored anywhere** — channels and roles resolve by name every run. 429s honoured off `retry_after` (body first, `Retry-After` header fallback), plus proactive parking on `x-ratelimit-remaining: 0`; every action (including `plan_*`, `skipped`, `rate_limited`, `superseded`) lands in `discord_calendar_log` keyed by `run_id`. Both tables are RLS staff-read / no-client-write (service role is the only writer). **Bot token is a function secret** — not `VITE_`-prefixed and nothing under `supabase/functions/` is in the Vite build. `npm run discord:calendar:test` runs 19 in-memory tests (fake supabase incl. the unique constraint + fake Discord) covering dedupe, edit-not-repost, cancellation, reminder windows, the 4xx-vs-ambiguous reservation rule, and the 24h retirement (an event inside 24h opens no `reminder_24h` row, and the surviving 2h reminder still fires on the first tick inside its own window and exactly once).

- **`supabase/config.toml` pins `verify_jwt = false` for every pg_cron-invoked and capability-URL Edge Function.** `cron-notify`, `send-push`, and `discord-calendar` are invoked by pg_cron/pg_net with a shared secret in a custom header (`x-push-secret`/`x-cron-secret`), never a user JWT; `calendar-feed`, `parent-response` and `event-family` are capability URLs authenticated by an unguessable token, never a JWT (`event-family` also takes the event hub's hourly pg_cron tick, checked against its own `x-cron-secret`). All six need `--no-verify-jwt` at deploy or the API gateway rejects every call before the function body runs. That flag used to live only in code comments and deploy-command reminders — easy to drop on a deploy someone runs without `--no-verify-jwt` — so `config.toml` now makes the CLI apply it automatically per function. `invite-member`, `send-approval-email`, and `send-parent-request` are invoked with the caller's own signed-in JWT (staff-authorization or ownership checks happen inside the function against that JWT) and are deliberately NOT listed — they keep default JWT verification on.

- **THE TWO DISCORD RENDERERS DISAGREE ABOUT SUBTEAMS ON PURPOSE, AND ARE NOT BEING RECONCILED.** `supabase/functions/discord-calendar/lib/render.js` matches a **curated alias map** (`SUBTEAM_ROLE_ALIASES`, 11 aliases to 7 roles) over **title + notes** and emits **Discord role names**. `api/_lib/weekAhead.js` matches the **canonical 12-value `src/subteams.js` vocabulary** over the **title only** (an explicit `Subteams: A, B` line in title or notes overrides it outright) and emits **app subteam names**. **The role set is smaller than the subteam set on purpose.** The reason is what each output DOES. The calendar reminder's output PINGS a role, and only a role that actually exists in the guild can be pinged, so its list is bounded by SERVER_SPEC §3 and a subteam with no role must resolve to nobody rather than to a broken mention. The week-ahead's output is TEXT A STUDENT READS, sitting beside the very same subteam names in frc-app, so it uses the canonical vocabulary and would be wrong to show a student a Discord-only name like Business/Media. The scope difference follows from the same split: the curated alias list contains no common English word, so title+notes is safe for it, whereas the canonical vocabulary contains `Management`, `Media`, `CAD` and `Fabrication`, and running those over notes prose ("Electrical runs wire management") attributed sessions to Management, which is simply false. **Do not try to make the two lists match.** Widening the alias map is correct only once the corresponding Discord role actually exists.

- **Week-ahead schedule post** (`api/discord-week-ahead.js` + `api/_lib/weekAhead.js`; `vercel.json` `crons`). One Discord post every Sunday evening naming the coming Mon-Sun week, so routine schedule information stops arriving as a same-day server-wide ping. **This re-establishes `api/`**, which had been deleted when the Discord calendar poster was ported off Vercel to a Supabase Edge Function; `vercel.json`'s SPA rewrite is narrowed to `/((?!api/).*)` again so it cannot swallow the function. **Cadence is enforced IN the function, not in the cron expression**: Vercel Hobby crons are daily-granularity (a day-of-week field is not honoured), so the cron fires daily at `0 1 * * *` UTC (which is 5 PM or 6 PM the PREVIOUS LA day either side of DST, so it always lands on that day's evening) and the handler no-ops with a 200 + reason on any day that is not Sunday in America/Los_Angeles. Auth is `Authorization: Bearer <CRON_SECRET>`, compared as sha256 digests so the check is constant-time and length-independent; anything else is a 401. **`allowed_mentions: { parse: [] }` is the hard guarantee.** The post cannot resolve `@everyone`, `@here`, a role or a user even if one of those strings is in an event title (verified by seeding exactly that). Reads `public.events` by OVERLAP (`starts_at < windowEnd and ends_at >= windowStart`, so a competition that opened the Sunday before still appears) and `public.tasks` where `status = 'open'` and `due_date` is inside the window. **Server credential is `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY`**, matching every other server-side reader here (calendar-feed, cron-notify, discord-calendar, parent-response): `events` RLS is `select to authenticated using (true)` with NO anon policy, so the anon key cannot read the schedule at all and a cron has no user session to be authenticated as. **An empty window still posts**, stating plainly that nothing is scheduled, because silence is indistinguishable from the job having failed. `?dry=1` renders and returns the body without posting and without needing `DISCORD_WEBHOOK_URL`; `?at=<ISO>` forces the evaluated instant and is **gated to the dry path only** so it can never shift which week goes out for real. **No secret is ever logged, echoed or returned.** A `scrub()` helper strips any occurrence of `CRON_SECRET`/`DISCORD_WEBHOOK_URL`/`SUPABASE_SERVICE_ROLE_KEY` out of anything bound for a response or the console (proved at runtime against a stand-in webhook that echoes all three back in its error body: 0 occurrences survive); the two "is not set" errors name the VARIABLE, never a value. **`events` has NO subteam column**, so subteam attribution reads the text staff already write, in two signals: an explicit `Subteams: A, B` line in title or notes wins outright, otherwise a word-bounded vocabulary match against the **TITLE ONLY**. Title-only is deliberate and was found by running the dry run: the nearest prior art (`discord-calendar/lib/render.js`) matches title+notes but against a hand-curated alias list containing no common English word, whereas this matches the full 12-value `src/subteams.js` vocabulary, which contains `Management`, `Media`, `Fabrication` and `CAD`. Over notes prose reading "Electrical runs wire management" it attributed the session to Management, which is false. A title names what a session IS; notes are prose. Imports `SUBTEAMS` from `src/subteams.js` rather than copying it. Generated copy is pure ASCII with no em dashes.

- **Discord announcements** (`supabase/migrations/0003_discord_announcements.sql` + its test, `supabase/functions/discord-announce/index.ts`, `src/discordAnnounce.js`, `src/AnnouncePage.jsx`/`.css`; 2026-10-01). `/announce` is admin-only (decision 35): compose, tick roles from `discord_announce_roles` (names and role ids an admin copies from Discord by hand; nothing guesses an id), add a poll or an embed, preview, "Check with server", confirm and send; the last 20 sends come from `discord_announcements`, which only the function's service role writes. `allowed_mentions` is always `{ parse: [], roles: [the ticked ids] }`. The function checks `is_admin()` with the caller's own JWT and carries a byte-for-byte copy of the builder's marked region, held identical by `tests/discord-announce-drift.test.js`; it uses the calendar poster's bot secrets. **Not live until** 0003 is pasted, the function is deployed by hand WITH JWT verification (`npx supabase functions deploy discord-announce`, never `--no-verify-jwt`; it is deliberately absent from `config.toml`), the bot role gets View Channel, Send Messages, Embed Links and Send Polls in #announcements, and the role list is filled in; until then the page says what is missing.

- **The two Discord renderers disagree about subteams ON PURPOSE and are not being reconciled.** `discord-calendar/lib/render.js` matches a curated 11-alias map over title+notes and emits Discord ROLE names, because its output pings a role and only an existing role can be pinged. `api/_lib/weekAhead.js` matches the canonical 12-value `src/subteams.js` vocabulary over the TITLE ONLY and emits app subteam names, because its output is text a student reads. The scope difference follows: the canonical vocabulary contains `Management`, `Media`, `CAD` and `Fabrication`, and running those over notes prose ("Electrical runs wire management") attributed a build session to Management, which is false. **Do not try to make the two lists match.**

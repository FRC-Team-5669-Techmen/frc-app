# Subteams

Moved verbatim from `CLAUDE.md` (The subsystems) on 2026-10-19, so `CLAUDE.md` stays short. `CLAUDE.md` links here; keep this file current in the same commit as any change to what it describes.

- **Subteam vocabulary** (`src/subteams.js` + `supabase/subteams_vocabulary.sql` + `supabase/subteams_tasks_constraint.sql` + `supabase/subteams_add_strategy_management.sql`). ONE canonical list, imported by ProfilePage (the profile chips), JobsPage (the job-form select), and MemberApplication (the three ranked choices) — no file keeps its own copy. **12 values, byte-for-byte: `Mechanical`, `Electrical`, `Programming`, `CAD`, `Fabrication`, `Media`, `Business/Outreach`, `Drive Team`, `Robot Construction`, `Field & Pit`, `Strategy and Scouting`, `Management`.** The last two were APPENDED (2026-08-23, `supabase/subteams_add_strategy_management.sql`) for the nine subteams named at the first team meeting — purely additive, no existing value renamed and no row rewritten. **Widening the vocabulary means widening BOTH CHECKs in one pass** (`member_applications_subteam_values_chk` and `tasks_subteam_values_chk`), and the two earlier migration files were extended to match so re-running one cannot silently revert the addition. `member_applications.subteam_first/second/third` are DB-constrained (`member_applications_subteam_values_chk`, re-pinned by `subteams_vocabulary.sql`, **NOT VALID when legacy application rows exist** — historical answers are left unrewritten, no lossless mapping). **`tasks.subteam` is now DB-constrained too** (`tasks_subteam_values_chk`, nullable-aware, same NOT-VALID-if-non-canonical-rows-exist pattern, added by `subteams_tasks_constraint.sql`); **JobsPage's job form is a real `<select>`** restricted to the canonical list — editing a job that already holds a non-canonical value keeps that one value selectable+selected (so an unrelated edit doesn't silently retag it), new jobs only offer canonical values. **`profiles.subteams` (text[]) is DELIBERATELY left unconstrained** — stores these literals with **no DB constraint**, so renaming/recasing/repunctuating an entry silently orphans live rows with no error; `subteams_tasks_constraint.sql` audits its distinct values (report only, no write) for staff to review by hand — append new values, never edit one in place without a data migration. **Every grouping/sorting consumer is data-driven, not list-driven** — `presence.js` `groupBySubteam` (A→Z + UNASSIGNED last, shared by PresenceBoard + ParentHomePage), RosterPage's subteam sort, JobsPage's group ordering, and `readiness_summary`'s project_staffing all read whatever value is stored, so new values need no per-consumer change and there is no color/icon/order map keyed to the list.

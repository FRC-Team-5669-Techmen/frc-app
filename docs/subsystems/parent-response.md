# Parent response

Moved verbatim from `CLAUDE.md` (The subsystems) on 2026-10-19, so `CLAUDE.md` stays short. `CLAUDE.md` links here; keep this file current in the same commit as any change to what it describes.

- **Parent response flow** (`supabase/parent_responses.sql` + `supabase/parent_responses_rls_test.sql` + `supabase/functions/send-parent-request/` + `supabase/functions/parent-response/` + `src/ParentResponse.jsx`/`.css` + `src/applicationFields.js`). Supplementary support info collected from a parent after their student applies. **It GATES NOTHING**: the application is complete without it and no student is ever blocked by a parent who does not answer. Five questions — weekend supervision (saturdays/sundays/either/neither), meal support and competition driving (yes/no/maybe), employer name, and a donate/lend note — plus a separate `employer_contact_consent` opt-in. **Employer name and consent are two controls, never one**: consent is an explicit checkbox defaulting off and is NEVER inferred from a named employer (enforced in the Edge Function too: only a literal `true` counts). **`member_applications.parent_token uuid not null default gen_random_uuid()` unique** is the capability key. **The column lockdown is the load-bearing part**: the student writes their own application row and the table has a select-own policy, so a readable token would let a student answer the form as their own parent. **Note that a plain `revoke select (col)` does NOT do this** — effective column privileges are the UNION of the column ACL and the table ACL, so a column revoke against a role holding table-level SELECT is a no-op. `parent_responses.sql` therefore **drops the table-level SELECT/INSERT grant on `member_applications` and re-grants every other column individually** (generated from the live catalog, so the file is re-runnable). Two consequences: **(a)** a column added to `member_applications` later gets no grant at all until the file is re-run, and **(b)** `select('*')` errors with "permission denied for column parent_token", so both client call sites (MemberApplication prefill, ApplicationsPage list) use the explicit `APPLICATION_SELECT` list in `src/applicationFields.js` — **keep that list in sync with the table**. FLAG: `supabase/calendar_token.sql` hides `profiles.calendar_token` with the naive column revoke and is subject to the same no-op; left alone (different table, different consumers, its own migration). **`parent_responses`** (one row per application, `unique (application_id)`, FK `on delete cascade`; the three enumerated answers are nullable so "did not answer" stays distinct from "no"/"neither"; `submitted_at` + `updated_at` where updated_at is null until an overwrite). **RLS is select-to-staff and nothing else** — no insert/update/delete policy for authenticated or anon, so the Edge Function's service role is the only writer, and a student can never read their own parent's answers. `parent_responses_rls_test.sql` is a rollback-safe mutation test with the same shape as the applications one: non-staff can't select or insert, non-staff can't read `parent_token` even on their own row, anon has no privilege, plus two positive controls (staff CAN read the row; non-staff CAN still read the rest of their own application) so neither a broken-shut policy nor an over-wide revoke can fake a pass. **`send-parent-request`** (JWT-verified, `invite-member` shape, Gmail SMTP via denomailer like `send-approval-email`): the body's `application_id` is a pointer, never a claim — the caller's id comes from the user-scoped client and ownership is decided server-side; a **staff caller may resend for any application** (`is_staff()`), which is the resend path. Plain-text email, no HTML, subject "Your student signed up for FRC Team 5669"; link is `APP_URL` + `/parent/<token>`; skips quietly (200) if the Gmail secrets are unset. **`parent-response`** (**deploy `--no-verify-jwt`** — a capability URL like `calendar-feed`): `fetch` returns only the student's name + any existing response, `submit` upserts on application_id and stamps `updated_at` on an overwrite (the token stays valid so a parent can correct answers); **every enumerated field is validated server-side** against the same vocabulary as the CHECKs; an unknown token returns a **generic 404** that never distinguishes wrong from expired. **Public route `/parent/:token`** is a sibling of `/` and `/login` above the auth-guard wrapper, and is excluded from both the AccessGate and application-gate early returns in App.jsx so a signed-in visitor can't get it swallowed; `ParentResponse.jsx` is an AccessGate-shaped standalone card (loading / form / submitted / invalid / offline) that **never touches a Supabase table**. Wiring: `MemberApplication` submit now does `.select('id').single()` and invokes `send-parent-request` — **a send failure never fails or rolls back the submission**, it surfaces as a note. `ApplicationsPage` surfaces response status at both list levels: a **Parent response table column** (responded + date, or Pending with an inline resend button) and the detail modal (all six fields read-only + its own resend). A **"Pending parent response only" filter** + a stats-strip count give staff the outstanding list without opening each row. **Employer contact consent renders as a colored badge** (`ap-consent-yes`/`ap-consent-no`, shown next to the employer name whenever one is on file) in both places — deliberately loud, since a named employer with consent is a legal sponsorship ask and without it is not, and the two must never be visually confusable. Resend state (`sending`/`sent`/`skipped`/`failed`) is keyed by application id in one `resendStates` map shared by every row's button and the modal's, so concurrent resends on different rows don't collide; a confirmation auto-clears after 4s so the control re-enables itself. The CSV export was extended with the parent response columns (responded, date, and the six fields) — still one row per member, via a `_response` merge done at export time only.

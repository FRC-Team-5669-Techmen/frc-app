# Parent dashboard

Moved verbatim from `CLAUDE.md` (The subsystems) on 2026-10-19, so `CLAUDE.md` stays short. `CLAUDE.md` links here; keep this file current in the same commit as any change to what it describes.

- Parent dashboard + guardian links (`supabase/guardian_links.sql`). `guardian_links(parent_id, student_id, created_by)` links a parent to students; staff manage links on RosterPage (parent-role members get a Students section) via `link_guardian`/`unlink_guardian` SECURITY DEFINER RPCs. RLS: readable by staff or the parent themselves, writable by staff only; a `lh parent select` policy lets a parent read their linked students' `logged_hours` (other tables were already authenticated-readable). `/dashboard` renders `ParentHomePage` (per-student live status/hours, a link to `/certifications` for their certifications, + read-only team glance) for `(hasRole('parent') && !isStaff)`; NavBar shows only Dashboard + Team Hours for that case. Shared hours math lives in `hoursUtils.js` (`computeHoursMs`/`fmtDuration`). **Self-service parent linking** (`supabase/parent_link_requests.sql`): a parent (the parent-view dashboard) searches the roster and submits a link request via `request_parent_link(p_student, p_note)` (own pending row, idempotent — reuses an existing pending request); staff review pending requests on `/access-requests` (a "Parent link requests" section under the access queue) and `approve_parent_link`/`deny_parent_link`. **Approve is idempotent**: the guardian_links insert is `on conflict do nothing` and the status update always runs, so one click reliably links (the old failure mode was a PK violation aborting the txn so status never moved → "approve twice, still failed"). `parent_link_requests` RLS: staff read all / parent reads own; all writes via the SECURITY DEFINER RPCs. The NavBar staff pending badge counts access_requests + parent_link_requests + cert_requests (the third kind came with cert requests, the skills bullet below).

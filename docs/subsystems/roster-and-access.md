# Roster, access and capabilities

Moved verbatim from `CLAUDE.md` (The subsystems) on 2026-10-19, so `CLAUDE.md` stays short. `CLAUDE.md` links here; keep this file current in the same commit as any change to what it describes.

- Admin roster (`supabase/admin_member_management.sql`): manage roles (student, mentor, lead, admin, parent) and status (active, inactive, alumni), gated by has_role('admin'). **Role grant/revoke goes through the `admin_set_member_role(p_member, p_role, p_grant)` SECURITY DEFINER RPC** — a direct client delete on member_roles silently affects 0 rows (no error) when the write policy doesn't match, so edits looked applied but never persisted; the RPC enforces admin server-side and raises loudly. Roster has text search (name/nickname/email) + sort (name/subteam/role/hours). **Nickname is the display name across the roster**, full_name fallback; `admin_get_members()` now returns nickname. **`admin_delete_member(p_member)`** hard-deletes a member behind a type-the-full-name confirm dialog: it nulls actor references (reviewer/creator/certifier/added_by/assigned_by/overridden_by cols) then deletes the profile (cascades attendance, hours, skills, task_claims, signups, study, push, guardian links, position assignments, roles) and the auth user (session_reviews + auth.* cascade) — no orphans; can't delete yourself.

- Access-request system + `parent` role (`supabase/access_requests.sql`). Non-allowed-email sign-ins hit a request form (replaces the old AccessGate dead-end) that writes an `access_requests` row; staff review at `/access-requests` and Approve (with assigned role student/mentor/parent) or Deny via SECURITY DEFINER RPCs. Approve whitelists the email in `approved_emails`; `claim_profile()` approval order is domain → approved_emails (grants the stored role) → already-approved (still defaults to student). Approval sends a courtesy email via the `send-approval-email` Edge Function (Gmail SMTP via denomailer; secrets `GMAIL_USER` + `GMAIL_APP_PASSWORD`, optional `EMAIL_FROM`/`APP_URL`) — approval never fails if those are unset. boscotech.edu still auto-approves as student.

- Staff invite flow (parent-friendly, additive to the request flow): the `/access-requests` page has an "Invite someone" panel that calls the `invite-member` Edge Function — it whitelists the email in `approved_emails` with a role (default parent) and sends Supabase's built-in one-tap invite link via the project SMTP, so the invitee clicks through and lands in already approved (no request/wait). Falls back gracefully if they already have an account. Requires Supabase Auth **Custom SMTP** configured and the app URL in Auth → URL Configuration (Site/redirect URLs).

- **Member capabilities** (`supabase/migrations/0004_member_permissions.sql` + its test, `src/permissions.js`; 2026-10-01). Per-person permissions an admin grants and revokes on `/roster`: `capabilities` is a lookup table, so a later capability is a new row, and `member_permissions(member_id, capability, granted_by, granted_at)` is written only through `admin_grant_capability` / `admin_revoke_capability` (`is_admin()` in the body; direct writes revoked). The first capability, `events.create` ("Can add calendar events"), adds three policies on `events` beside the untouched staff one: an approved holder may add events as themselves, never mandatory, only into their own series, and may edit or delete only those, while they still hold it. `/schedule` offers the form, Edit and Delete only where the server will accept them, and says so when a write is refused at 0 rows. A holder's event is an ordinary event: it reaches Discord, push, the week-ahead post and the calendar feed, and a `build` one opens the shop card (decision 32). Before 0004 the roster reads "Not set up yet" and the schedule is unchanged.

- **`src/claimApproval.js`** (2026-10-01): `nextApproval`, `nextRoles` and `nextOnboardedAt` decide what `App.jsx` keeps when `claim_profile`, `member_roles` or `profiles` is read again, which happens on load and on every auth event (supabase-js emits one on each return to the tab). A failed read never downgrades what the tab already holds for that member, so a student mid check-out is not shown the access gate and a mentor is not put behind the student application; with nothing held, unknown roles fail the application gate open (decision 40). Pinned by `tests/checkout-approval.test.js` and `test:checkin` steps R8 to R10.

# Scheduling

Moved verbatim from `CLAUDE.md` (The subsystems) on 2026-10-19, so `CLAUDE.md` stays short. `CLAUDE.md` links here; keep this file current in the same commit as any change to what it describes.

- Scheduling module (`supabase/events.sql`). `events(title, kind, starts_at, ends_at, location, notes, ...)` — readable by all authenticated, writable by `is_staff()` (plain staff-write policy, no RPCs; no RPC creates events anywhere, and a repeating series is one client-side bulk insert), and once migration 0004 is applied also by a holder of the `events.create` capability under three narrower policies (the member capabilities bullet below). **Event kinds**: `build`/`meeting`/`competition`/`potluck`/`outreach`/`volunteering`/`training`/`other` — defined in `SchedulePage.jsx` `KINDS` + the `events_kind_check` constraint (`volunteering` added via `supabase/categories_reduce_event_kind.sql`, `training` via `supabase/events_kind_training.sql`; `events.sql`'s inline CHECK is re-pinned to the full list so a fresh install matches). Each is styled by a `.sch-kind-<kind>` class, surfaced as a text label in the per-event rollups, and carries a `KIND_COLORS`/`KIND_LABELS` entry in `supabase/functions/discord-calendar/lib/render.js` (`training` → 'Training'; an unknown kind falls back to `other`/'Event' rather than throwing). **The kind vocabulary is duplicated across those four sites with nothing enforcing agreement — adding a kind means touching all of them.** The `calendar-feed` function and `ReportsPage` pass `kind` through generically and need no change per kind. **No event kind has an emoji anywhere** — the schedule pill is the uppercased raw kind string, Discord uses a colour + text footer. Only `build` opens the shop (`SHOP_OPEN_KINDS`). `/schedule` is an agenda list grouped by day (all roles view; staff, and `events.create` holders within their policies, create/edit/delete via a form; past events behind a toggle). **Shop open/closed rule:** the shop is "open" only during today's `kind='build'` event windows (other kinds do not open the shop); status is "Open until END" inside a window, "Closed, opens START" before the first, else "Closed today", with a live "N checked in" override from `presence.js`. The shop-status derivation (`shopStatus.js`) and the glance data (`useGlance.js`) are shared: ParentHomePage renders `GlanceCard.jsx`, and HomePage builds its own tiles from `useGlance`; the `/checkin` fast path deliberately imports none of it. Event times render in America/Los_Angeles via `toLocaleTimeString`. **Calendar Phase 1** (SchedulePage): in-memory Month/Agenda view toggle (there is no Week view; Agenda is the default under 640px wide and Month at 640px and up, decision 21), a "My events" filter (events RSVP'd going + every shop-open `SHOP_OPEN_KINDS` session) across both views, and form conflict signaling (non-blocking warning naming time-overlapping events, excluding the edited one) + FULL capacity badges on Month chips and event heads. Month uses LA day-key (`dayKey`) bucketing with UTC-based date math (`addDays`/`addMonths`) so they never drift on DST; event rows are a shared `renderEvent`/`renderDayGroup` so RSVP behavior is identical everywhere. **Calendar Phase 2 — iCalendar subscription feed** (`supabase/calendar_token.sql` + `supabase/functions/calendar-feed`): `profiles.calendar_token uuid` (unique, auto-defaulted on every row) is a capability key. The token column is **revoked from client select/update** (profiles is broadly authenticated-readable and RLS is row-scoped, so a `profiles(calendar_token)` embed would otherwise leak everyone's token); a member reads/rotates only their OWN token via SECURITY DEFINER RPCs `get_calendar_token()` / `rotate_calendar_token()`. The `calendar-feed` Edge Function (self-contained, **deploy `--no-verify-jwt`** — it's a no-JWT capability URL, authenticates by `?token=`) serves a hand-rolled RFC 5545 `.ics` (CRLF, 75-octet folding, text escaping, UTC `DTSTART`/`DTEND`, per-event `UID`/`SEQUENCE`/`LAST-MODIFIED` from `updated_at`; no RRULE since series rows are pre-expanded); `?scope=mine` (default) mirrors the My-events filter, `?scope=all` is everything, both from 30 days ago forward; uses only `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`. ProfilePage has a "Calendar subscription" section (webcal one-tap link, https add-by-URL field + Copy, mine/all scope toggle, Regenerate).

- Event RSVPs / signups (`supabase/event_signups.sql`). Additive columns on `events`: `rsvp_enabled` (bool), `capacity` (int null). New `event_signups(event_id, member_id, response[going/maybe/declined], item, …)`, PK (event_id, member_id) — one upserted row per member per event. RLS: readable by all authenticated; insert/update/delete gated to `member_id = auth.uid() OR is_staff()` — plain own-row writes, **no RPCs** (reserve the RPC pattern for cert-gated/privileged transitions). Any approved member (student/parent/staff) can RSVP. The RSVP control + attendee list render inline on `/schedule` **only when `rsvp_enabled`** (non-RSVP events are visually unchanged), reusing the existing schedule UI. Capacity is **informational** (shows "N of CAP", soft-warns when full) — it does NOT hard-block; strict-limited slots would need a row-locking sign-up RPC (follow-up).

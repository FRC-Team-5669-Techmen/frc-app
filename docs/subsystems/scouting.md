# Event scouting

Scouting is an additive, lazy-loaded part of Techmen at `/scouting` and `/scouting/:eventId`. Records reference existing `events` and member profiles. No check-in import is added. The existing protected shell supplies feedback.

## Data contract

See [contract](../scouting/CONTRACT.md), [evidence](../scouting/EVIDENCE.md) and [verification](../scouting/VERIFICATION.md). Claim, observation, assignment, message, personal list and external team data are separate record kinds. Every correction stores a new version, preserving the prior value and actor. Missing answers are never zeros. Individual FUEL contribution is never inferred from an official alliance total.

All writes call `scouting_save` through `writeVia`; new scouting has no legacy direct-write fallback. Operation IDs deduplicate retries. Optimistic version checks reject stale corrections rather than silently overwriting another tab. The connector calls the same SQL operation and adds its own audit trail.

Domain conflicts use SQLSTATE `PT409` (HTTP 409). Application-raised `40001` loops on hosted PostgREST 14, so it is no longer emitted for stale/missing/duplicate scouting records. The client recognizes both codes and holds either proposal for explicit review. Synchronization publishes the durable queue with refreshed evidence, so a new conflict cannot open review against the previous server value. `docs/scouting/HOSTED_HTTP.md` documents the real hosted Auth/REST/Edge harness and its isolated fictional identities; OTP/OAuth, successful providers and real delivery remain separate acceptance work.

## Access

Approved active students and staff may scout. Parent-only accounts cannot access scouting, including through capability grants; a parent holding mentor, lead or admin is staff. Managers are staff, event scouting leads or holders of `scouting.manage`. Individual observations and pick lists remain author-owned. Shared pit and assignment changes have explicit manager gates.

## Offline behavior

Open the app and event while online before entering the venue. Cached event records and IndexedDB drafts/operations are scoped to the signed-in member and event. Local capture is not server synchronization. Synchronization is not Discord delivery. Pending proposals survive reload; conflicts require an explicit reviewed correction. A revoked account cannot continue uploading, and changing accounts never uploads the previous account's queue. External footage is not downloaded for offline use.

## Setup and verification

Apply migration 0022 only after the existing chain through 0021. Until its schema is installed, the page shows a setup state through `schemaMissing`. Edge integrations deploy separately by hand. No production database change or production deployment was performed. Temporary isolated hosted staging was verified and deleted after evidence capture; see `docs/scouting/STAGING.md`.

Training prepares students for mentor assessment; it does not write IDEA certification rows or revive the retired skills system. Certification remains an IDEA Classroom action.

## Planning, replies and practice

Managers can paste a match schedule or accept the imported schedule, choose a match range and available scouts, mark breaks, preview workload/coverage, and save the shift. Existing work is kept and uncovered robots are visible. Local batch enqueue is atomic; server authorization/conflicts remain per record. `scouting_roster` provides only eligible names and is event-manager gated.

Pit conversations support separately attributed replies with immutable original-thread links. Comparison voting has side-by-side evidence cards. Pit addresses display their source, time and freshness warning. Training now saves incomplete decisions, active mission, simulation answers and real-footage worksheets as drafts; completion does not award certification.

The standalone review is built by `npm run scouting:preview` from the same route and fixture backend. `npm run scouting:preview:check` checks the compiled bundle under DOM emulation. Neither is a deployment or substitute for native browser/phone checks.

## Recovery and evidence quality

`Export event data` now includes account/event-scoped drafts, practice, pending operations, confirmed receipts and cached evidence in a versioned JSON archive. The archive is for reviewed recovery; it never automatically uploads or overwrites existing work. Offline event opening skips remote data queries. Team imports are atomic locally.

Prior-event footage must retain its source event and full match key, appears with a provenance label and stays outside current-event reliability percentages. Full TBA and short current-event match labels share one logical identity. The coverage panel in Teams finds missing pit reports, thin or disputed evidence and prior-event context.

## Built PWA recovery

The scouting route and installed start URL have a service-worker navigation fallback. After an eligible online event load confirms `scouting_can_access`, a local identity hint remembers only member/event IDs and preparation time. Cold offline scouting opens that account's cached data and durable queue, including when Auth needs a network refresh. It does not grant server authorization. Explicit sign-out, account changes and an online access denial clear the hint. Reconnection returns to normal auth/approval and server actor/RLS checks before upload. First-time offline login and uncached events are unavailable. The identity hint can be cleared without deleting pending evidence.

`tools/e2e/scouting-pwa.mjs`, run through the disposable SQL harness, uses a normal production build, real Chromium/IndexedDB/service worker, real Supabase JS and local PostgREST/native PostgreSQL. Only Auth identities/token issuance are synthetic; no provider or Discord call is made. This separately verifies cold navigation, expired-session offline entry, lost-response retry and HTTP permission/connector boundaries. See the current verification record for actual results.

## Training evidence and account isolation

The practice workbook freezes a source/team/match, first-pass answers and notes, then appends separate reviewed corrections. Unknown and unrecorded remain distinct. Mission completion is withdrawn when its required acknowledgment, reflection or answers change. Practice export waits for durable state and explicitly awards no certification. The retained browser spec completes all eight missions and verifies the exported packet; simulated partner acknowledgment is not human assessment.

Offline entry requires both the prepared identity hint and the current locally stored Supabase session's member ID to match. Reading that ID does not refresh or expose a token. Sign-out/account changes and cross-tab storage updates close the prepared surface. A queued `syncing` operation left by a closed page is retried automatically after its IndexedDB lease expires, with the original operation and actor IDs.

## Pit navigation

Teams includes a Nexus v1.8.0 geometry map and text directory with search, highlighting, zoom and rotation. Download explicitly while online; normalized geometry/key/source/time are stored in the existing member/event draft store and included in event backups. Failed provider/schema/storage refreshes preserve the previous map. Walls, labels, areas, rotated pits and single/double arrows are rendered as bounded data, never upstream SVG/HTML. Scout pit reports remain separate; contradictory locations are flagged and never automatically overwritten.

`scouting-import` accepts read-only `mode: pit_map` for eligible members viewing a competition/training event; its default roster preview remains manager-only. Both paths authenticate and use caller-scoped Supabase clients. The connector's existing preview tool supports the same optional mode. This adds no migration and no public writes. See `docs/scouting/PIT_MAP.md` for independent coordinates and external acceptance limits.

## Reviewed pending-save recovery and large events

An exported event JSON can be previewed and selectively restored under the same account/event. Recovery validates bounded request identity, preserves original operation bodies/IDs and atomically rechecks collisions. Recovered operations stay held and out of evidence until separately released and confirmed by the server. The archive cannot install a cache, permission hint or alleged receipt. Practice, unsubmitted drafts and maps remain available in the JSON for manual review, not automatic restoration. See `docs/scouting/RECOVERY.md`.

Form/planner/pick-list draft-read failures pause editing until retry; failed storage never produces a saved-success message. Dialog cleanup returns keyboard focus. Team evidence cards page in groups of 30; roster search, downloaded cache, percentages and rankings still use all records. The retained `scouting-volume.mjs` and `scouting-accessibility.mjs` harnesses distinguish synthetic local browser checks from field acceptance.


## Confirmed evidence and reviewed match briefs

`projection.js` separates confirmed rows (downloaded data plus newer verified queue receipts) from optimistic local edits. Strategy rates, master ballots, filters, coverage and match briefs use confirmed inputs. Pending corrections retain earlier confirmed evidence. Actor/event checks, recovered-proposal holds and monotonic receipt versions have executable permissive mutation controls.

`ObservationBrowser.jsx` makes all downloaded observations searchable/pageable, with current/prior/disputed filters and existing author-only correction controls. `currentObservations` is shared with reliability so dispute grouping uses the same normalized identities and correction rules. `EvidenceRecord.jsx` retains attribution and revision history.

`MatchBrief.jsx` saves a device-local actor/event draft, requires a manually confirmed six-team lineup, exposes capabilities/unknowns/disputes and coach plans separately, and freezes JSON/escaped printable HTML only after review. Plan/evidence changes invalidate export readiness. Read/write failure pauses editing or review; writes are serialized and only the latest completed write may claim saved. No new remote permissions, notifications or SQL contracts. See `docs/scouting/DECISION_SUPPORT.md` and the retained decision-support checks.

A definitive 42501/PGRST301/account-change response hides the event surface, including old confirmed queue receipts, until access is restored. Local records/drafts remain intact. DOM and native-browser denial/retry checks complement database permission checks.

Video observations with missing/invalid event scope are now excluded from current rates and match coverage, retained as raw evidence and surfaced through a dedicated review filter and explicit brief/comparison exclusions. Explicit live observations remain current even with an attached reference URL. Provenance tests independently fix the expected 0/1 versus 1/2 distinction; a permissive model mutation must be detected.

## REBUILT match fields (0027, ledger 0017)

A student tester: "This evidence/scouting material does not seem good, as I believe every robot does these areas." The three capability questions stay; an observation now also carries `payload.match` with the 2026 REBUILT fields: auto and teleop FUEL scored, teleop FUEL missed (counts), climbed in auto, shuttled, died, tipped, got stuck, broke a mechanism (yes, no, did not see), defense played (none, some, most) and its effectiveness and driver skill (1 to 5), the TOWER level (none, level 1 to 3, attempted and failed, did not see), and fouls or cards (a note).

- **A missing answer is never a zero.** A field is absent until recorded; 0 is an observed count ("Saw zero"); JSON null is refused by `scouting_private.validate_match`. Counts use +1, +5 and -1 steppers sized for one hand (`src/scouting/MatchFields.jsx`); tapping a selected choice clears it.
- **One field list**, `MATCH_FIELDS` in `src/scouting/match.js`; `tests/scouting-match.test.js` holds it equal to 0027's SQL. 0027 re-defines 0022's `validate` with one change (the `match` key on an observation); `0022_scouting_rls_test.sql` still passes 72/72 on top of it.
- **Summaries** (`teamMatchSummary`) use the module's projection rules: confirmed records only, current-event evidence only, one latest observation per author per match, then one value per match (the median of the scouts who watched it; a yes/no where scouts disagree is disputed and excluded). The team card, the three-team comparison and the pick-list filters (`MATCH_FILTERS`) read it; an unrecorded value never passes a minimum.
- **Before 0027 is pasted** the page calls `scouting_match_fields()`, finds it missing, and the form shows the capability questions with a "starts when migration 0027 is pasted" line. The answer is cached per event for offline starts.
- **Download spreadsheet** (`src/scouting/spreadsheet.js`): two CSVs beside the JSON recovery archive, one row per observation (every field, scout, match, team; empty cell for not recorded) and one row per team (the confirmed summaries).
- **Training**: a ninth mission, "Count it, or leave it blank", with its drill; the practice match lab grades match fields beside the capabilities, and a recorded 0 where nothing was seen is graded wrong.

## Pairs, super scouts and match-number shifts (0030, ledger 0022)

How elite FRC teams scout, built season-agnostic: nothing below names REBUILT except the match fields it reconciles.

- **Coverage modes.** The planner's "Scouts per robot" is One per robot (six per match), Two per robot (needs 12 or more robot scouts) or Auto (pairs only at 12+). `coveragePerRobot` and `PAIR_MIN` in `src/scouting/schedule.js`. An existing assignment or observation fills one slot of a pair. No scout ever gets two robots in one match. 0022's assignment index was already unique per assignee, so pairs needed no SQL.
- **Pair reconciliation** (`src/scouting/pairs.js`): per team per match with two or more scouts, counts and ratings are averaged and a field is flagged when the two differ by more than 10 FUEL (counted by fives, so two taps) or 1 rating point, or give different decisive yes/no or choice answers (did not see never disagrees). For two scouts the average equals the median `teamMatchSummary` already uses, so the team card and the pairs sheet agree. Download spreadsheet adds a third CSV, one row per pair, `Check` or `Agree`, naming both values.
- **Super scouts.** One or two per alliance per match, chosen in the planner's own "Super scouts" list (a person is a robot scout or a super scout on a shift, never both). Their assignment is one row per alliance: `payload.role = 'super'`, `alliance` (red is the first three scheduled teams, TBA order), `teams`. The sheet (`SuperScoutForm.jsx`) rates driver skill, defense, speed and intake reliability 1 to 5 per robot, plus failure notes; an unrated field is absent, never 1. Each rated robot saves one observation with `role: 'super'` and `payload.super`, no counts and no capability answers (0030 refuses both). `model.js currentObservations`, `coverage.js` and the planner exclude super notes from every rate, count and robot coverage; `superSummary` shows them on the team card and beside each team in the pick list.
- **Shifts by match number.** Shift blocks are qualification match ranges (Q1 to Q12, block size 6 to 20) chosen in the planner, never clock times, so a late field breaks nothing. `src/scouting/shifts.js` reads the number from every key form (`2026cabb_qm12`, `qm12`, `Q12`, `12`); playoff and practice keys have none. The **Now panel** on Scout this (`ShiftNow.jsx`) shows the match on the field, the current block, who is on shift (robot scouts and super scouts) and "You're up in N matches" for the signed-in member. A manager moves it with +1, -1, Set and Block; everyone polls every 30 seconds and keeps the last value for offline.
- **Server (0030).** `scouting_private.validate` re-defined from 0027 with the role/super/alliance/teams rules and `validate_super`; `public.scouting_now` (RLS on, no policy, every client privilege revoked) read through `scouting_now_get` (any eligible scout) and written through `scouting_now_set` (managers; set, atomic bump or block size; clamped 0 to 999) via `writeVia`. Before 0030 is pasted the Now panel says "starts when migration 0030 is pasted" and super saves are refused by the old validate; nothing else changes. Proof: `0030_scouting_shifts_super_rls_test.sql` (27 checks) and `tools/sql-harness/mutants-0030.mjs` (13 permissive mutants); client rules in `tests/scouting-shifts.test.js`.
- **Practice without an event.** `/scouting/practice` (linked from the event list) opens the full Training path with no event loaded, scoped to the account and the fixed `practice` key on this device. Training lessons now cover pairs, super scouts and match-number shifts.

**Event-day hardening (ledger 0029).** Waiting saves (local, or failed and retryable) are sent again every 60 seconds while the page is open and the browser says online, because venue signal is often weak but present and the `online` event never fires; operation ids keep it idempotent. Typed qualification labels are stored as `qm<n>` (`canonicalMatchKey`). Manage event's TBA key fills itself from the imported teams' `source_url` (`importedMapKey`). A cold start that cannot reach the server shows "Can't reach the team server" with Open offline scouting for a prepared device (`App.jsx` `ServerUnreachable`), never the access request form.

No SQL limit ever existed; see `docs/history/scouting-feedback-0028b.md`.
- **Saved confirmation** (`SavedBar` in `ScoutingPage.jsx`): after any form save, a bar sticky at the bottom of the page says what was saved and follows it through the durable queue (on this device, synced, not synced and why). It stays until dismissed.
- **Team card order** (`src/scouting/spread.js`, `TeamEvidence.jsx`): capabilities and observation options whose answers vary between observed robots come first, marked; answers every observed robot (two or more) shares fold into one line each with the robot count and this robot's figure. ## Observation options (0037, ledger 0029)

One team-wide list of extra questions on every observation, chosen by the scouting lead, beyond the built-in REBUILT fields: yes/no, pick one (2 to 8 answers), count, rating 1 to 5 or a short note, each in a phase (auto, teleop, endgame, reliability, strategy). Scouts see the "Observation options" card on the Scout tab (what is on, and Suggest an observation) and a "Saw something no question covers? Suggest one" button inside every observation, which sends the team, match and note with the request. The lead's card lists requests to review (Turn on, Edit first, Decline with a reason), what is on (reorder, edit, turn off) and what is off (turn back on), and adds new options directly. Answers are `payload.custom` (absent when skipped, never zero; null refused) and are summarized one value per match on team cards and in both spreadsheets. Rules shared by client and server: `src/scouting/options.js` and `scouting_private.validate_custom`; a type never changes once used and a used choice is never removed. `public.scouting_options` has RLS on, no policy and every client privilege revoked; it is read through `scouting_options_list()` and written through `scouting_option_request(...)` and `scouting_option_save(...)` via `writeVia`. The list is cached per event on the device for offline scouting; suggestions and changes need a connection.

## Pick board and live alliance selection (0042, ledger 0032)

`/scouting/:eventId/board` (`src/scouting/PickBoard.jsx`, linked from the top of Pick lists). One screen for choosing partners: on a laptop three columns that each scroll on their own (teams, alliances, team detail) and fit the window; on a phone the same three as tabs.

- **The order is automatic** (`src/scouting/pickRank.js`, pure). Value = points a robot adds per match: FUEL is an OPR fit on TBA's alliance HUB points (`hubScore.totalPoints`), regularized toward the team's 2026 season (`solveRidge`, lambda 2); TOWER points are exact per robot from `autoTowerRobotN` / `endGameTowerRobotN`; without a breakdown, one OPR on the match score. Our scouting adjusts it: breakdowns (died, broke, stuck, tipped, shrunk toward 10 percent) lower it by up to half the rate, scouts' hand counts carry at most 30 percent and only with 2 or more matches, scouts' median tier moves it 3 to 6 percent, and most scouts saying do not pick lowers it 15 percent. The pick score is what the team adds to OUR alliance: three robots play, so the gain in the sum of the best three, plus a quarter of the team's own value, plus defense (more with "We want a defender").
- **The season prior** is shipped with the app per event, `src/scouting/priors/<event key>.json`, made by `node tools/scouting/season-prior.mjs --event 2026cabl` from The Blue Alliance's public event pages (no key): an OPR per 2026 event, the latest weighted most. Statbotics skips offseason events and answered 500/503 on 2026-10-28; when the import returns an EPA it replaces the prior.
- **People's input**: managers mark Must pick (top), Avoid (bottom), a bump of plus or minus 5 points a tap, and a strategy note, per team (`state.overrides`). The Auto column always shows the data-only position, with the arrow a mark caused. Scouts rate teams one at a time in Pick lists, Rate teams (four buttons, about 40 taps for 40 teams), which saves their own `pick_list`; the board reads every scout's tiers as votes.
- **Results**: a manager taps Pull results (the `scouting-import` preview, TBA matches with breakdowns), saved compact to `state.matches`; while a manager has the board open before selection it pulls again every 3 minutes.
- **Live selection** (`src/scouting/draft.js`, pure): the selection is a log of picks and declines replayed from seeds (captains from `rankingFromMatches`, average RP then average score, editable in setup). Rounds alternate 1 to 8, 8 to 1, 1 to 8 (Beach Blitz: 3 rounds, four-team alliances); a captain picked by a higher captain dissolves that alliance and the next seed becomes the last captain; a declined team can never be picked; undo drops the last entry. One manager records each pick (one tap on the row, or Enter); every device polls the board every 5 seconds. A pick saves with the selection version it read, and a stale version is refused (40001), so two operators cannot overwrite each other. The odds column is the chance each team is still there at our next pick, from 300 simulated drafts where other captains pick by value with noise (seeded, so every device shows the same odds).
- **The judge** (`node tools/scouting/replay.mjs`): real 2026 alliance selections from TBA, scored by where each actual pick sat in our ranking of the teams still available. Measured 2026-10-28 on 10 events (211 picks): round 1 picks were in the board's top 3 for 79 to 83 percent (mean rank 2.4 to 2.8), against plain event OPR 73 to 79 percent, the season prior alone 46 to 50 percent, and a random choice's mean rank of 14 to 16. Later rounds agree less (captains pick for fit), which is what the role score and the marks are for.
- **Database (0042)**: `scouting_pick_board`, one row per event, RLS on with no policy and every client privilege revoked; read through `scouting_pick_board_get` (anyone who may scout), written through `scouting_pick_board_save(event, section, value, team, expected)` (managers only) with sections override, selection, matches and settings. Before 0042 the board still ranks from the prior and the scouting records and says the shared part is not set up.
- **Proof**: `0042_scouting_pick_board_rls_test.sql` (25 checks) and `tools/sql-harness/mutants-0042.mjs` (10/10 permissive mutants caught); `tests/pick-rank.test.js`, `tests/pick-draft.test.js`; `tools/e2e/features/pick-board.mjs` on fixture mode, where `features/pickboard.js` answers a 2026cabl roster import with 60 deterministic qualification matches over the real 42 teams.
